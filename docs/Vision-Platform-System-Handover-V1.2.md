# Vision Platform 工业视觉智能平台交接手册（V1.2）

> **更新日期：** 2026-09-03  
> **代码分支：** `develop`  
> **适用对象：** 平台开发、算法工程、实施运维、产线质量人员  
> **阅读顺序：** 本文 → 根目录 `README.md` → `docs/OCR-Service-Handover.md` → `docs/Vision-Platform-Operation-SOP.docx`

## 1. 平台定位与边界

Vision Platform 用于汽车电子装配中的**错装、漏装、混装**检测。它采用“配方路由 + 固定 ROI + 多能力检测 + 确定性规则 + 可选 VLM 复核”的结构。

- 平台不是“上传整图后由大模型自动判定一切”的系统。
- 配方决定当前拉线、物料、工序、相机和拍照次数应检查哪些区域与规则。
- AI 自动解析只用于配置辅助；生产检测主路径仍使用经用户确认的 ROI。
- 接口成功但产品不合格应返回 `code=0`、`result=NG`；模型或系统异常返回 `result=ERROR`，不得伪装为 `NG`。
- 当前不覆盖划痕、污渍、裂纹等表面缺陷，也不直接控制相机、PLC、运动轴或光源。

## 2. 当前架构

```text
相机软件 / 文件服务器
        │  上传图片，调用 /api/detect
        ▼
Vision Platform :9010
  ├─ 配方路由（拉线、物料、工序、相机、拍照次）
  ├─ 基准点/特征点对齐
  ├─ 固定 ROI 裁剪
  ├─ 并行检测执行与规则汇总
  ├─ 记录、候选基准、统计报表
  └─ 模型服务管理
        │
        ├─ DINOv2 :9022        相似度/特征向量
        ├─ PaddleOCR :9024     专用文字识别
        ├─ OpenCV（平台内）     颜色与图像质量
        ├─ Qwen3-VL :9023      规则复核、双图审核
        ├─ Grounding DINO :9021 自动解析候选框
        └─ SAM2 :9025          线束等区域分割辅助
```

模型服务独立运行，主平台通过 HTTP 调用。模型异常不会使平台进程退出；但该检测项必须返回 `ERROR`，不能作为合格结果。

## 3. 核心功能模块

### 3.1 配方与路由

一个已发布配方的业务定位字段为：

```text
line_code + material_code + operation_code + camera_code + capture_index + version
```

配方编码示例：`L01_PDU001_OP10_CAMERA1_PICTURE1_V1`。

生产接口保留供应商约定的 `/api/detect`，不破坏既有 `sn` 和 `image_paths` 参数；同时支持可选结构化字段：`line`、`materialcode`、`operation`、`camera`、`picture`。匹配优先级为：

1. 请求中的结构化字段；
2. 图片文件名解析，例如 `CAMERA1PICTURE1`；
3. 已配置的唯一默认配方。

当无法唯一匹配配方时必须返回配方错误，而不是使用错误配方继续检测。

### 3.2 工作台与 ROI 配置

工作台：`http://127.0.0.1:9010/workspace`。

- 上传图片后由用户点击“自动解析”，不会自动提交模型推理。
- 可由 Grounding DINO、Qwen3-VL 和 SAM2 生成候选物体；候选框仅作建议，可删除、移动、缩放后再保存。
- 支持鼠标中心缩放、拖动平移、双击还原；前端显示坐标使用原图坐标系，缩放不应改变保存的 ROI 坐标。
- 每个 ROI 可配置名称、对象类型、是否为对齐基准及三类校验规则：**物体存在、OCR 文字、颜色**。
- 当前生产定位模式只有固定 ROI，界面不暴露未实现的动态定位模式。
- 规则测试在当前页面下方展示 ROI 裁剪图、基准图（如有）、规则、主模型输出、VLM 输出及最终结论，不应跳转编辑页面。

### 3.3 图像对齐

实际生产中允许小范围平移和轻微旋转。执行顺序：

1. 若配方指定“对齐基准 ROI”，在其周边搜索 ORB 特征，使用匹配点与 RANSAC 估计轻量仿射变换；
2. 校验内点数、内点比例、缩放、旋转和位移是否在安全范围内；
3. 成功后将整图变换至配方基准坐标系，再按固定 ROI 裁剪；
4. 基准点失败时回退至全局相位相关的平移补偿；
5. 两种方式均不可信时保留原图并在调用结果中记录原因。

对齐基准应选择稳定、不被线束遮挡的特征，例如定位孔、固定螺钉组合或 PCB 丝印；不要选择可变标签、线束、铜排或反光区域。每个配方仅允许一个基准 ROI。

相关环境参数在 `.env` / `.env.example`：

```text
IMAGE_ALIGNMENT_ENABLED=true
IMAGE_ALIGNMENT_MAX_SHIFT_RATIO=0.05
IMAGE_ALIGNMENT_MIN_RESPONSE=0.08
IMAGE_ALIGNMENT_ANCHOR_SEARCH_MARGIN_RATIO=0.35
IMAGE_ALIGNMENT_ANCHOR_MIN_INLIERS=8
IMAGE_ALIGNMENT_ANCHOR_MIN_INLIER_RATIO=0.35
IMAGE_ALIGNMENT_ANCHOR_MAX_ROTATION_DEGREES=8
```

该能力不用于修复大幅透视变化、严重失焦、遮挡或相机重新安装后的标定变化；遇到这些问题应重新采集配方基准图并核对治具/相机。

### 3.4 检测规则与并行执行

一个 ROI 可以同时配置多条规则。不同能力应并行执行：OCR、颜色和相似度互不依赖时并行请求，最终由规则引擎汇总。

| 校验类型 | 主能力 | 说明 |
|---|---|---|
| 物体存在 | DINOv2 参考相似度 | 比较当前 ROI 与该配方/区域的参考特征；适合稳定工装和外观变化有限的对象 |
| OCR 文字 | PaddleOCR | 使用专用 OCR 服务；支持预处理、旋转候选、缩放、对比度与锐化增强 |
| 颜色 | OpenCV | 基于 ROI 生成/保存颜色特征后进行比较；不是只比较用户输入的颜色名称 |

**相似度不能单独保证“存在”。** 对于螺钉锁付、线束卡扣、空位等临界对象，应使用“局部存在 ROI + 参考特征 + 结构/颜色/OCR”等至少两种证据组合；若无法满足，应优先改进拍照、光源或引入专用小模型，不应不断放宽阈值。

### 3.5 OCR 服务

OCR 采用专用 PaddleOCR 服务，不由 Qwen3-VL 代替。当前本地默认使用 PP-OCRv5；服务配置已预留 PP-OCRv6（服务器建议使用 v6 medium）。

OCR 预处理包含：裁剪放大、灰度/对比度、锐化、阈值候选、90/180/270 度旋转候选与结果过滤。它对清晰、近似平面、字符高度足够的标签有效；弯曲线束、强反光、字符过小、严重倾斜时仍可能误识别。

迁移 OCR 时不能只复制一个 `ocr_service.py`：还需复制 `ocr_service/` 目录、模型文件、Python 依赖、环境变量、启动脚本及服务管理配置。详细见 `docs/OCR-Service-Handover.md`。

### 3.6 VLM 复核与双图审核

Qwen3-VL 使用同一套 `:9023` 服务完成两类任务：

1. **规则复核**：对某条已配置规则，按“每次复核”或“仅低置信度复核”策略执行；
2. **候选基准双图审核**：比较当前合格 ROI 与已有基准图，判断是否适合进入候选池。

这是同一个模型服务、不同提示词和任务类型，不应为了这两种用途重复部署两个 Qwen3-VL 服务。

复核策略：

- **每次检测都复核**：忽略复核上下限，每次调用 VLM。
- **仅低置信度复核**：主模型分数低于下限直接 `NG`；处于上下限之间才执行 VLM；高于上限采用主模型结果。
- **测试当前 ROI**：启用复核时始终执行 VLM，便于界面同时比较结果。

VLM 的输出只能作为复核证据或风险信号，不是质量真值。VLM 可能存在幻觉、提示词敏感、版本变化和图像细节遗漏；当主模型、规则或 VLM 结果冲突时，应输出 `UNCERTAIN/ERROR` 或进入人工复判队列，不能为了“自动化”强制判 OK。

### 3.7 候选基准与参考向量

检测任务中，某 ROI 的所有主规则均为 `OK` 时，系统会尝试收集其 ROI 图作为候选基准。候选收集经过以下保护：

- 图像质量检查；
- 感知哈希去重；
- 候选池数量限制（默认每个 ROI 保留约 20 张）；
- Qwen3-VL 双图审核；
- 用户在候选列表中人工提升为正式参考，或拒绝/清理。

候选图不是立即成为正式标准图。高相似度也可能把持续性误装、错误配方、错误 ROI、错误参考或系统性拍摄问题逐步带入基准，因此保留人工确认入口。

正式参考图经 DINOv2 提取为 embedding（特征向量）。向量以按配方业务层级组织的 `.npy` 矩阵文件和 `.json` 清单保存；数据库保存组标识、路径、维度、模型版本和来源。检测时只读取当前配方/ROI 对应的向量组，计算余弦相似度，采用 **Top-K 鲁棒聚合**，而不是只取全库最大值。这样减少单张异常参考图误导，同时避免随着产品增多全库扫描。

参考图与向量不需要无限累积。建议每个稳定 ROI 保留 10–30 张代表图，候选池独立保留有限数量；历史检测原图按数据保留策略归档或清理。

### 3.8 检测记录与统计报表

检测记录保存：请求参数、配方、图片、每个 ROI 的规则和结果、模型处理输出、VLM 输出、耗时、对齐信息和最终状态。接口结果只需要向供应商返回 ROI 名称和检测明细，不需要暴露 ROI 坐标。

记录列表支持按产品条码（SN）筛选。报表页面支持用户选择日期范围（最大 366 天），按以下维度展示：

- 拉线；
- 物料；
- 工序；
- 整体每日趋势。

页面采用本地 SVG 图表展示每日检测量和 NG 率；不再依赖外网 CDN。当前“准确率”只能表示**经人工/下游真值确认后的准确率**。系统自动生成的 OK/NG 率不是模型准确率，不能混用。

建议后续为调用记录增加来源标识：`PRODUCTION`、`RECIPE_TEST`、`API_TEST`、`SIMULATION`、`MANUAL_REVIEW`；统计报表默认只统计 `PRODUCTION`。未引入真实复判结果前，报表只展示过程指标，不应声称模型准确率。

### 3.9 模型服务管理与日志

“模型服务”菜单提供各模型服务的地址、端口、健康状态、启动/停止和日志查看入口。服务标准输出（正常运行信息）和标准错误输出（异常、警告、堆栈）都带时间戳；日志面板自动滚动到最新内容。

常见端口：

| 服务 | 地址 | 健康检查 |
|---|---|---|
| 主平台 | `http://127.0.0.1:9010` | `/api/v1/health` |
| Grounding DINO | `http://127.0.0.1:9021` | `/health` |
| DINOv2 | `http://127.0.0.1:9022` | `/health` |
| Qwen3-VL | `http://127.0.0.1:9023` | `/health` |
| PaddleOCR | `http://127.0.0.1:9024` | `/health` |
| SAM2 | `http://127.0.0.1:9025` | `/health` |

出现 `502 Bad Gateway` 时，优先检查对应模型服务是否已启动、端口/URL 是否与 `.env` 一致、模型目录是否存在、显存是否足够，以及该服务日志中的启动异常。

## 5. 部署与迁移

当前在 Windows 本地调试；代码按 Linux/RHEL 8.3 部署兼容方式组织。迁移时：

1. 迁移源代码、`requirements.txt`、`config/`、启动脚本、静态资源和 `docs/`；
2. 单独迁移模型文件和数据目录，不提交模型权重到 Git；
3. 按服务器 CUDA、GPU 驱动和 Python 版本重新建立虚拟环境；
4. 修改 `.env` 中模型目录、数据目录、服务地址和端口；
5. 先启动模型服务并逐一访问 `/health`，再启动主平台；
6. 使用一份已知图片调用 `/api/detect` 做端到端验证；
7. 生产前配置 systemd、日志轮转、磁盘监控和备份策略。

模型下载来源必须使用官方渠道，模型权重不纳入 Git：

- Grounding DINO: https://huggingface.co/IDEA-Research/grounding-dino-base
- DINOv2 Base: https://huggingface.co/facebook/dinov2-base
- Qwen3-VL-4B-Instruct: https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct
- PaddleOCR: https://github.com/PaddlePaddle/PaddleOCR
- SAM2: https://github.com/facebookresearch/sam2

## 6. 验证与交接检查

完成迁移或模型升级后，至少执行：

1. 所有服务 `/health` 返回可用；
2. `python -m unittest discover -s tests`；
3. 固定图片的配方测试：物体存在、OCR、颜色各至少一例；
4. 基准点轻微平移/旋转测试，确认 ROI 仍正确裁剪；
5. 供应商 `/api/detect` 回归，验证字段、文件名解析和返回兼容；
6. 检查检测记录、模型调用结果、候选图和日期范围报表；
7. 检查断开外网后页面仍能加载本地 CSS/JS。

## 7. 已知风险与后续建议

1. **OCR 可见不等于可稳定识别。** 线束曲面、小字、反光与焦深问题优先通过镜头、曝光、补光、分辨率和 ROI 设计改善；软件增强只能补偿一部分。
2. **相似度不是完整的存在检测。** 缺件、锁付、遮挡等关键场景需要多证据规则或未来引入小型专用模型。
3. **VLM 不可作为真值。** 只做复核、双图审核和复盘抽样；必须保留人工复判与真实质量反馈。
4. **候选池需要治理。** 合格结果可自动收集候选，但正式参考图应保留审核、版本、去重和有限容量。
5. **对齐有安全边界。** 基准点质量不佳时应拒绝错误变换；不能借对齐掩盖治具、相机或工件定位异常。
6. **准确率需要真值。** 没有人工复判、返修或下游质量结果时，平台只能报告 OK/NG 率、错误率和模型分数分布，不能证明漏判率。

## 8. 建议的下一阶段

1. 为检测记录引入来源和人工复判状态，并把下游质量真值回写到报表；
2. 增加低置信度/冲突结果队列，优先由质量人员复判；
3. 对高风险线束锁付、空位、插接到位场景建立专用 ROI 组合规则或训练轻量模型；
4. 在 RHEL 8.3 上完成 systemd、日志轮转、自动恢复、GPU 监控和数据备份；
5. 将候选基准审核和参考版本变更纳入可追溯流程。
